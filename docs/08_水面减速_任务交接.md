## 2. 目标与边界

### 要做

- 幸存者进入水中，按**水面高度**降低可移动速度（踩水/涉水）。
- 水越深越慢；离开水立即恢复；换图/持久化/预设都一致。
- **只影响幸存者**（team 2，含 bot 幸存者）；感染者、特感、Tank 等完全不变。
- 默认值、菜单、配置、预设、状态页、静态验收、运行时验收全部接入。

### 不做 / 先别做

- 不改 `sv_maxspeed`、`sv_friction` 等**全局** cvar：那会连带影响特感（历史 0.4.6 的教训，见 `cs2movement_move.sp` 里 SetupMove 的 survivor gate 注释）。
- 不改武器表、不改受伤减速公式、不改 cs2feel。
- 不在客户端侧做（没有客户端 hook；纯服务器玩法）。
- 不新增第三层菜单/值页；参数仍行内循环。

### 需要 Owner 拍板

1. **默认是否开启**：建议开发期默认 `enable 0`，验收 PASS 后再改 `1`；或直接 `1`，但必须先跑完水面实测。
2. **水位 3（游泳）是否也减速**：L4D2 游泳可能不走 `m_flMaxspeed`，先测；如果不生效，决定“跳过 level 3”还是换路径。
3. **“水面高度”定义**：用 `m_nWaterLevel` 的 3 档（推荐），还是要连续水面 Z 高度（需要 trace，成本/不确定性高）。

关键路径：

```text
CPlayerMove::SetupMove (DHook detour)
  → for each survivor
  → CS2M_MoveEngineTarget(i)          ← 单一时速来源
       weapon table → cap → CS2M_InjuryApply
  → 写 m_flMaxspeed
  → 引擎复制到 CMoveData

CS2M_MoveDesiredMaxSpeed(client, buttons)   ← Stage 2 / 状态读数
  weapon table → walk/duck 倍率 → cap → CS2M_InjuryApply

crouch/slide
  → CS2M_MoveEngineTarget(client) 取 runTarget 作为上限
```

**只影响幸存者的现成门控**：

```sourcepawn
stock bool CS2M_IsSurvivor(int client)  // team 2
```

SetupMove 循环里已有 `if (!CS2M_IsSurvivor(i)) { g_iSkipNotSurvivor++; continue; }`；
`CS2M_MoveApplyPlayerSpeed` 也先判 `CS2M_IsSurvivor`。新代码沿用，不要另造 team 判断。

**速度叠加顺序**：`武器表 → walk/duck/cap → CS2M_InjuryApply`。
水面减速建议加在 **`CS2M_InjuryApply` 之后**，即最终乘数，保证与蹲/走/受伤叠乘，而不是互相覆盖。

## 4. 架构约束（先解决，再写功能）

`src\feel\` 与 `src\movement\` 都是 `tools\sync_sources.ps1` 生成：

- 输入：`..\CS2FeelVScript_L4D2\plugin_src`、`..\CS2Movement_L4D2.public\scripting`
- 机械重命名后写入 `src\`；`verify.ps1` 会跑 `sync_sources.ps1 -Check`，`src\` 与“上游 + 重命名表”不一致就失败。
- **直接改 `src\movement\*.sp` 会在下一次 sync 被覆盖，而且 verify 会报 drift。**

### 推荐：加一个本地 patch 层

在 `tools\`（或 `patches\`）增加：

```text
patches\movement_water\
  cs2movement_water.sp      # 新文件，sync 直接复制到 src\movement\
  apply.ps1                 # 对 cs2movement.sp / move / config 做确定性文本插入
```

`sync_sources.ps1` 在“复制 + 重命名”之后调用 `apply.ps1`；`-Check` 模式也在内存里应用同一 patch 再比较。这样：

- 上游保持只读；
- 水面功能有独立文件；
- 未来上游升级只需重跑 sync + patch + 测试；
- `verify.ps1` 能证明 patch 仍在。

### 不推荐

- **直接改上游 `CS2Movement_L4D2.public`**：最快，但上游不再是只读；下次更新会覆盖，交接成本高。除非 owner 明确接受“本地 fork”。
- **在统一层再加一个 SetupMove detour**：两个 detour 链式顺序不可控，容易和 movement 的 pre-hook 打架。
- **在 `OnPlayerRunCmd` 里改 velocity**：move 模块已经证明这条路径在 L4D2 被引擎重新加速（历史 refuted 路径），不要重试。

## 5. 推荐实现（2 个参数）

### 5.1 ConVar

在 movement 侧（patch 的 `cs2movement_water.sp` 或 `cs2movement.sp`）创建：

```text
cs2movement_water_enable     0/1    默认 1（或验收前 0，见 §2）
cs2movement_water_slowdown   0.0..0.8  默认 0.35
```

- 只加 2 个：`CS2U_MAX_PARAMS 40`、`CS2U_MAX_ENTRIES 40`，当前 37；39 刚好。
- 如果 Owner 要 3 档独立倍率（4 个参数）→ 必须把两个 cap 都抬到 ≥41（并改 docs/verify），不建议在第一版做。
- 名字沿用 `cs2movement_*`；不要叫 `cs2u_*`，这是 movement 行为。

### 5.2 水位读取

```sourcepawn
int level = 0;
if (HasEntProp(client, Prop_Send, "m_nWaterLevel"))
    level = GetEntProp(client, Prop_Send, "m_nWaterLevel");
else if (HasEntProp(client, Prop_Data, "m_nWaterLevel"))
    level = GetEntProp(client, Prop_Data, "m_nWaterLevel");
```

- Source 语义：`0` 不在水、`1` 脚踝、`2` 腰、`3` 眼/游泳。
- 先写一个临时 debug 输出确认 L4D2 上确实有该 netprop、且值随水深变化；不要假设。
- 若 netprop 不存在/不更新：备选是 trace 水面 Z（`MASK_WATER`），但贵且易错，作为 fallback，不作为首选。
- 每 tick 每玩家读一次即可；`GetEntProp` 很便宜。需要缓存就按 `GetGameTickCount()` 缓存。

### 5.3 倍率

```text
factor = 1.0 - slowdown * (level / 3.0)
```

| level | 含义 | slowdown=0.35 |
|---:|---|---:|
| 0 | 干地 | 1.000 |
| 1 | 脚踝 | 0.883 |
| 2 | 腰 | 0.767 |
| 3 | 眼/游泳 | 0.650 |

- `level <= 0`、`enable=0`、目标速度 <= 0 时直接返回原值。
- 夹紧 `factor` 到 `[0.05, 1.0]`，避免负速度。
- 只对 `CS2M_IsSurvivor(client)` 且 `IsPlayerAlive(client)` 生效。

### 5.4 接入点

在 `CS2M_MoveEngineTarget(client)` 末尾（`CS2M_InjuryApply` 之后、`return` 之前）：

```sourcepawn
speed = CS2M_WaterApply(client, speed);
```

在 `CS2M_MoveDesiredMaxSpeed(client, buttons)` 末尾同样加一行（保持 Stage 2 / 状态读数一致）。

- SetupMove 已经只遍历幸存者；`CS2M_WaterApply` 内部再判一次，防未来调用点漏门控。
- crouch/slide 通过 `CS2M_MoveEngineTarget` 取 runTarget，水面倍率会自动传导，不需要在 crouch 文件重复写。
- 不要改 `CS2M_MoveApplyPlayerSpeed` 的写属性路径；engine 模式默认开启，属性路径默认关闭。

### 5.5 已知边界

- `cs2movement_weapon_speed_mode 0` 时 `MoveEngineTarget` 返回 -1，水面功能不生效；先按“该模式本来就是原生速度”记录，不强行接管。
- 游泳（level 3）如果 `m_flMaxspeed` 不生效：先测；必要时**level 3 不减速**（只做 1/2），或改为独立的 swim 速度路径。不要在没测的情况下写 velocity。
- 与受伤减速叠乘：受伤先降，再乘水面；两者都只降不升。

## 8. 风险 / 未决

1. **`m_nWaterLevel` 是否存在/更新**：第一个要验证的事实；不存在就 trace，不要猜。
2. **游泳（level 3）不吃 m_flMaxspeed**：L4D2 的水中移动可能走独立路径；先测，必要时 level 3 跳过。
3. **patch 机制成本**：`sync_sources.ps1` 需要支持 patch + `-Check`；这是本任务的主要工程风险，不是玩法代码。
4. **容量**：`CS2U_MAX_PARAMS`/`CS2U_MAX_ENTRIES` 都是 40；2 个参数刚好，4 个必须扩容。
5. **默认值**：新玩法默认开可能改变现有服务器手感；建议验收前 0、PASS 后 1。
6. **bot 幸存者**：`CS2M_IsSurvivor` 包含 bot；bot 进水也会减速；如果 Owner 只要真人，另加 `!IsFakeClient`（不建议，和现有 movement 不一致）。

## 11. 实施记录（2026-11-07，1.0.10）

### 11.1 三个拍板的结论

| 问题 | 结论 | 理由 |
|---|---|---|
| 代码放 patch 层还是 fork 上游 | **patch 层**（`patches\movement_water\`） | 上游保持只读；`sync_sources.ps1` 写模式与 `-Check` 跑同一变换，`verify.ps1` 能证明补丁仍在；将来上游升级只需重跑 sync |
| 默认是否开启 | **默认开启 1 / 0.35**，`vanilla` 预设显式 0 | 机制验证（曲线、gate、菜单、落盘）已在测试服通过；水面减速是“补回原生行为”，不是实验性物理。关掉只需一行 `enable 0` |
| level 3（游泳）是否减速 | **公式包含 level 3，但标注未实测** | 曲线是连续量，单独给 level 3 开洞会让“水更深反而更快”这种反直觉出现；若实测证明游泳不吃 `m_flMaxspeed`，再按 §5.5 处理 |
| “水面高度”定义 | **`m_nWaterLevel` 三档**（不用 trace） | 见 §11.4：netprops/datamaps 都存在，零额外成本；trace 会在干地上误判，比不生效更糟 |

### 11.3 关键实现细节（给后来者）

- 叠加顺序：`武器表 → cap → CS2M_InjuryApply → CS2M_WaterApply`。两个调用点（`MoveEngineTarget` /
  `MoveDesiredMaxSpeed`）都必须加，否则蹲下滑行的 runTarget 与状态读数会和引擎写值不一致。
- `CS2M_WaterApply` 内部重复 `CS2M_IsSurvivor(client) && IsPlayerAlive(client)`，不信任调用点。
- prop 探测一次一客户端缓存（`Prop_Send` 优先，退回 `Prop_Data`），缺失时打一次 `WATER-NOPROP` 并永久 no-op，
  绝不用 trace 兜底。
- `slowdown 0` 是合法值（等于关），不要把它当“未配置”。
- 状态行里的 `slowdown=0.349` 是 float32 的 0.35（SourceMod 的 `%f` 截断），cvar 原始字符串是 `"0.35"`。
